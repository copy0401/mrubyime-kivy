# AGENTS.md

Android 形碼 IME 專案 `mruby-ime` ("小蝦米輸入法", pkg `com.example.mrubyime`). Input logic lives in embedded mruby behind JNI. The keyboard is a standard `TextView`/`LinearLayout` view hierarchy (no Canvas), built at runtime from a **Ruby keyboard DSL → IR JSON → Kotlin renderer** (`KeyboardRenderer`), not from the hand-written XML layout. Read `mruby-ime/README.md` (UX spec) and `mruby-ime/SKILL.md` (mruby/JNI/UTF-8 rules) before touching engine, bridge, or keyboard code, and update them when behavior changes.

## Layout

- `mruby-ime/` — the Gradle project; all real work happens here.
- `mruby-ime/app/src/main/mruby/mrubyime_engine.rb` — mruby core: `.cin` parsing, lookup, buffer state. **Build-time source only** — compiled into `engine_irep.c`; ships as bytecode, not as an asset. User Ruby engines are **removed** (the engine always runs the compiled bytecode).
- `mruby-ime/app/src/main/assets/keyboard_dsl.rb` — runtime keyboard DSL (Builder / ThemeBuilder / PageBuilder / BarBuilder / GroupBuilder / RowsBuilder / RowBuilder + JSON writer + validation). **Compiled to bytecode.**
- `mruby-ime/app/src/main/assets/keyboard_layout.rb` — built-in Chinese/English layout expressed in that DSL. **Compiled to bytecode.**
- `mruby-ime/app/src/main/assets/keyboard_layout.json` — IR generated at build time from the same DSL; used only as the fallback when the runtime DSL fails.
- `mruby-ime/app/src/main/cpp/` — `mrubyime_jni.c` (bridge), `engine_irep.c` / `keyboard_dsl_irep.c` / `keyboard_layout_irep.c` (generated bytecode), `CMakeLists.txt` (links `mruby-ime/mruby/build/android-arm64-v8a/lib/libmruby.a`).
- `mruby-ime/app/src/main/java/com/example/mrubyime/` — IME service, `KeyboardView` (renderer host), `KeyboardRenderer` (IR → views), `KeyRowLayout` (span/weight/align geometry), `KeyFrameLayout` (full-cell touch bounds + visual gap insets), `RowsLayout` (row bands with half-gaps), `KeyboardLayout` (IR data classes + parser), `KeyboardLayoutRepository` (`ThemeResolver` + engine/asset/emergency fallback), `KeyboardLayoutFiles` (user `layouts/keyboard.rb` storage + Android/data mirror), `StepScrollView`, settings.
- `mruby-ime/app/src/main/res/layout/view_keyboard.xml` — **no longer inflated**; kept only so the `R.id.*` constants used by the renderer still exist. Do not treat it as the live layout.
- `mruby-ime/app/src/main/assets/mrubyime.cin` — the shipping built-in table: **uniliu 萬國蝦米_unifont_t** (2.0 MB: 30,478 codes / 47,788 `%chardef` entries + a 139,637-line `%phrase` list, every line `詞 權重`; `entries` reports 187,422). The single-char `%phrase` lines were **removed from the table** — a `%phrase` word of length 1 is also ignored by the parser, so 單字 order stays exactly `%chardef`'s and nothing can re-weight it by accident. Longest `%chardef` code 5; derived phrase codes up to 24. It is the **only** built-in table — `assets/dicts/boshiamy.cin` was deleted. Unlike the older build, `%phrase` is **one entry per line, `詞 權重`** (the upstream `uniliu.unifont.cin` shape): 139,637 multi-char words, each followed by its corpus frequency (`一 213167`, `你好 121`). That readability costs cold-load time — see the load numbers under "Engine / data-path facts".
- Root `make_project.sh` — **regenerates the whole project with `rm -rf mruby-ime/` first, and its output predates the current sources**. Never run it to make a change.
- Root `mrubyime-ime.zip` — old source snapshot (backup only); not used by the build.
- `mruby-ime/mruby/` (93 MB) + `3.3.0.tar.gz` are downloaded by `build_mruby.sh`; safe to delete (rebuild re-downloads, needs network).

## Build & verify (no tests, no lint, no CI)

- Full pipeline — mruby → ireps + JSON → APK → **installs onto the attached phone**:
  ```bash
  cd mruby-ime && ./build_all.sh
  ```
  It supplies the toolchain that is missing from the environment: `ANDROID_NDK_HOME=/home/cc/Android/Sdk/ndk/30.0.16248370`, `JAVA_HOME=/opt/android-studio/jbr`, and `~/.local/share/gem/ruby/3.4.0/bin` (where `rake` lives).
- APK only, no device side effects:
  ```bash
  cd mruby-ime && JAVA_HOME=/opt/android-studio/jbr ./gradlew assembleDebug
  ```
  Plain `./gradlew` fails (`java` is not on PATH). Verified working; APK at `app/build/outputs/apk/debug/app-debug.apk`.
- Release APK (signed with the debug key, so it installs **over** the debug build and keeps the user's edited `dicts/`/`layouts/` files):
  ```bash
  cd mruby-ime && JAVA_HOME=/opt/android-studio/jbr ./gradlew assembleRelease
  ```
  → `app/build/outputs/apk/release/app-release.apk` (**~1.2 MB**; was ~4.7 MB). Size pass: R8 minify + resource shrinking (no androidx — `LayoutFileProvider` replaces `FileProvider`), minimal-gem libmruby with `-Os`+LTO (`build_mruby.sh`, ~600 K .so raw / ~220 K compressed via `useLegacyPackaging`), WebP launcher icons, engine removed from assets. The signing config in `app/build.gradle.kts` points at `~/.android/debug.keystore` and is only applied when that file exists; `lint { checkReleaseBuilds = false }` is required — release-only `lintVitalAnalyzeRelease` fails on this toolchain. Swap the keystore before ever publishing.
- Verification is manual: install, enable the IME, type in the settings screen's test field. Only `arm64-v8a` is built — x86_64 emulators cannot load the JNI lib.
- On-device `Log.d` from this app is often filtered; use `Log.i`/`Log.e` for startup diagnostics (`layout JSON bytes=… parsed=true pages=[chinese, english]` is logged once per IME creation).

## #1 trap: editing any `.rb` does nothing by itself

Runtime executes the generated `*_irep.c` arrays, never the `.rb` files. After editing `mrubyime_engine.rb`, `keyboard_dsl.rb` or `keyboard_layout.rb`:

```bash
cd mruby-ime && ./build_mruby.sh    # host mrbc + arm64 libmruby.a + 3 ireps + keyboard_layout.json
```

Cheap syntax check without NDK/network: `mruby/build/host/bin/mrbc -Bengine_irep -o /tmp/x.c app/src/main/mruby/mrubyime_engine.rb` (same for `-Bkeyboard_dsl_irep` / `-Bkeyboard_layout_irep`). The mruby build config is written by `build_mruby.sh` into `mruby/build_config.rb` (**minimal gem list** — enum/array/hash/string/symbol/range/numeric/kernel/proc/object-ext + `mruby-sprintf` + `mruby-compiler`, `-DMRB_UTF8_STRING`, `-DMRB_ARY_LENGTH_MAX=0`, `-DMRB_GC_ARENA_SIZE=4096`, `-Os`+thin LTO, arm64 only); the root `build_config.rb` is unused. After changing the gem list, `rm -rf mruby/build/android-arm64-v8a` first — stale gem objects are not pruned.

## Engine / data-path facts

- Startup: `MrubyimeIME.onCreate` resolves only the table id + signature, then either **reuses the table a previous instance parsed in this process** (the mruby state is a C static that `onDestroy` leaves alone, so switching to another IME and back is `load=0ms` — `EngineCache`) or spawns the `engine-load` thread, which reads the whole `.cin` (`DictionaryRepository.loadActive()`: user `active.cin` → built-in `assets/mrubyime.cin` → `assets/dicts/<name>.cin`) and builds the engine there; the IME window appears immediately and `onEngineReady(loadMs, id)` (main thread) applies the metadata and rebuilds the layout from the runtime DSL. mruby builds the full 2.0 MB uniliu table in **~1.7 s** cold on the phone (was ~2.6 s before the 2026-11-22 memory pass; the `%phrase` block is ~84 % of it). There is **no parse-result cache** — a process start pays it again; `EngineCache` only covers service re-creation inside a live process. **Every main-thread path that touches mruby is gated on `@Volatile engineReady`** — the JNI state swap must never race a read. **`MRB_ARY_LENGTH_MAX=0`** is set in `build_mruby.sh` — mruby's default array cap (131,072) makes `Hash#values` raise "array size too big" on the huge phrase tables.
- **Memory (2026-11-22 pass, measured on the phone)**: the loaded table costs ~92 MB native (was ~135 MB). Root cause found with a host `mallinfo` harness: mruby `Hash#[]=` **dups unfrozen String keys** (hash.c:972), so every word existed as 3 objects and every code as 2 — 671k live strings for ~400k distinct texts. The engine now merges `@phrase_freq` into `@words` (`word → weight`, 0 = unweighted, `@weighted` flag), freezes words/codes/chars before storing (hash keeps the object), stores single-word `@phrases` buckets as bare Strings, and parses word-only `%phrase` lines via `getbyte`/`rindex`. `GC.start` ends `load_dictionary`; JNI `init` calls `mallopt(M_PURGE)` via dlsym. Host: per-load live 63.9 → 31.1 MB, load 1078 → 756 ms, composition −13 %, zero `slow input` lines over a 60-key burst. **`MRB_WORD_BOXING` adds nothing on top — don't add it for size.**
- **The engine is generic `.cin`, not 形碼-specific.** `mrubyime_engine.rb` parses `%ename`/`%cname`, `%selkey`, `%keyname`, `%chardef`; legal keys = `%keyname` keys ∪ code characters; max code = the table's longest code. Built-in **uniliu 萬國蝦米_unifont_t**: 30,478 codes / 47,788 `%chardef` entries (traditional + simplified) + a 139,637-line `%phrase` list (`詞 權重`), `%selkey 0123456789`, longest `%chardef` code 5. It includes `%space_style` (ignored).
- **`%phrase` has two forms, both optionally weighted; single-character words are ignored.** `<code> <word…>` (explicit, also builds `@phrase_prefixes` so a prefix completes) and **word-only** (`你好 您好`, each word derives its own code from `@code_of` via `derive_code`). Any word of length 1 is dropped in both forms **before** `derive_code` / weight bookkeeping, so a `%phrase` line can never reorder, duplicate or weight a code's own characters — 單字 order is exactly `%chardef`'s. The shipped table no longer carries such lines at all (they were its top cold-load cost); a user table that does pays only the parse. Word-only phrases go into `@phrases` (code → words) and the `@words` set but **not** into `@phrase_prefixes` — 139k prefixes would make every keystroke scan the whole phrase table. Derivation is required: 你's code `gns` has first candidate 妳, so 你好 is only reachable through the derived code `gnsgz`, not through composition. **Weight = a trailing decimal integer on the line** (`你好 121`, `一一九 21`), parsed only when the line has ≥2 fields and the last field is pure ASCII digits, so a one-field line that *is* a number stays a word. The weight lands in `@phrase_freq[word]` (multi-char words only — ~100,149 in uniliu); `@phrases` values stay plain string arrays. Auto-composition (`compose_candidates`) lists every segmentation, ranked word-set first, then weight (heaviest), then fewest codes, deduped; each code contributes up to **3** characters (`COMPOSE_CHARS_MAX`, `walk_segments`) instead of only its first, because 36 % of `%chardef` entries are non-primary homographs — with 1 char 17 % of the table's words could never be composed and typing an alternative code returned the wrong word (`wwnjn` → 違是, now 這是), 3 chars lifts composability 83 % → 98.6 % for ~1.5× branching that the 40,000-step budget absorbs (host 0.4–2.3 ms per key at 5–140 codes, P1/P2 included). **The walk runs in two passes, each with its own reading list and its own 4 tail heads**: a cheap canonical pass (one character per code, `SEG_BUDGET_CANON` = 3,000 steps) and then the 3-character pass. Without it a code that also happens to be a prefix of the intended split swallows the whole 120-reading cap first — `segnfooo` is `s|egn|fooo` (三峽區), but `seg` alone is also a code (綏), and its 3-character subtree starved the `s` branch so the word never showed up. Two passes make **every code a character has** usable: `segnfooo`, `segnfxx` (`s|egn|fxx`) and `segnfv` (the derived phrase key) all put 三峽區 first, and on 240 sampled `%phrase` words typed with random **non-shortest** codes the word lands in the top 16 193 times (was 154) and at number 0 154 times (was 115). A **half-typed last code** is completed too: `compose_candidates` records up to 4 finished prefixes per split point during the walk (`TAIL_HEADS`, cheap) and `tail_readings` then appends the codes that turn the reading into a table word, scanning only the bucket in **`@tail_index`** (built once at load: prefix → codes finishing it in ≤2 keys; ~14.4k slots, +~50 ms host on the background load). So `pnsg` shows **你好** instead of the literal 你機 (`g` alone is 機), `wwnj` shows 這是, and the guess is merged *after* the real readings so it can never crowd them out. `MAX_COMPLETIONS` is now **16** (chips beyond the 10 selkeys draw no index label so every chip keeps one width). `candidates_for`'s exact branch keeps **characters before phrases** and weight-sorts **within each group**, so a phrase never displaces the code's own characters; single characters keep `%chardef` order (`wr` → `0 測 1 测`), while auto-composed words still rank by weight (`gnsgz` → `0 你好 1 妳好`). With no weights in the table the map is empty and `rank_by_weight` returns the list untouched, so unweighted tables behave exactly as before.
- Selection keys come from `%selkey` (`selkeys[i]`, absolute across the whole candidate row, so `9` can commit a candidate that is scrolled off-screen). 形碼's first candidate is key `0` even though the soft key row reads `1234567890`.
- **A `%selkey` value may also be a radical** (注音 `%selkey 1234567890` + `1 ㄅ`…). The engine exposes `would_extend?(key)` (= `buffer+key` is a code or a prefix of one, backed by an `@prefixes` set), and `onKeyPressed` only lets such a key select when it can no longer extend the code, so `2 8 4` builds ㄉㄚˋ and `284` then `1` selects. Non-code `%selkey` digits (形碼) always select. A selection key with no matching candidate is swallowed. **With an empty buffer a digit that is not a legal key is committed as plain text.**
- Soft keyboard: 5 rows in both modes on a **12-column** grid. Row 1 is `1 2 3 4 5 6 7 8 9 0 - =` (swipe up → `! @ # $ % ^ & * ( ) _ +`); rows 2–4 carry the letters plus `[ ]`, `; ' \`, `, . / ` and 倒引號 (swipe up → `{ } : " | < > ? ~`, printed as each key's `sub_label`); row 5 is `中/英` (span 2) + Space (span 8) + `⏎` (span 2). Chinese rows show uppercase letters; English rows show lowercase. The Chinese bar is code box (weight 2) + candidates (weight 9) + hide `▼` (weight 1); in English it becomes a 12-key action bar (`TAB`, blank, `^A ^C ^V`, `⇧ ⇩ ⇦ ⇨`, `DT`, `W`, `▼`). Mode switching is the row-5 key, Space swipe-down or the hardware hotkey **Alt+Space / Shift+Space** (a bare Shift no longer toggles).
- `MrubyimeEngine#input`: lowercases and **appends** to the buffer (never truncates), but **stops resolving candidates once the buffer is past the current max code length** (`@max_code_len`, reset to the table's longest code on load, overridden over JNI by `set_max_code_len` — table max when 「最大碼清空組字」 is on, 140 when off). Auto-commit lives in `MrubyimeIME.onKeyPressed`, not in Ruby: `buffer.length >= min(4, table max) && candidates.size == 1 && !engine.canExtend()` (`can_extend?` checks every legal key, so a 4-code prefix of a 5-code is not committed).
- **Dead-code auto-clear**, two independent gates in `MrubyimeIME.onKeyPressed`:
  1. **「死碼清空編碼區」** (`clear_dead_code`, default **false**): a **1–3 char buffer with no candidates AND `engine.deadPrefix()` true** is cleared, where `dead_prefix` checks whether **adding ANY one of the active table's legal keys** still yields nothing. A prefix that can still grow is preserved; a provably dead one is cleared. `dead_prefix` is read-only. **Auto-composition keeps most buffers alive**: any buffer that reads as a run of single-char codes counts as composing (`compose_word`), so with the built-in table almost every legal-key sequence has candidates and the switch rarely fires — only leftovers that cannot segment are cleared.
  2. **「最大碼清空組字」** (`max_code_clear`, default **false** → max code 140): once the buffer reaches the current **max code length** (the active table's longest code when on, 140 when off) with no candidates it is cleared. With it off the buffer keeps growing and the code box shows only the **last 6 codes** while the engine holds the whole buffer.
- Candidates cross JNI as one `\n`-joined string (`inputSerialized`). Keep the serialized pattern.

## JNI / UTF-8 rules

- Output: `utf8_to_jstring` (`NewByteArray` + `new String(bytes,"UTF-8")`). Never `NewStringUTF` for non-ASCII (SKILL Rule B).
- Input: dictionary, keys and layout contexts cross JNI as `ByteArray` (raw UTF-8) and become mruby strings via `mrb_str_from_jbytes`; never `GetStringUTFChars` (Modified UTF-8).
- Wrap every call in `mrb_gc_arena_save/restore`; check `mrb->exc` after every `mrb_funcall` and drain it with `log_mrb_exception`.
- The engine lives in a C static: `mrb_gc_register` it after `mrb_obj_new`, or GC may collect it between calls.
- JNI surface is exactly `init(ByteArray)`, `inputSerialized(ByteArray)`, `backspaceSerialized`, `currentCandidatesSerialized`, `selkeys`, `buffer`, `reset`, `tableSize`, `deadPrefix`, `setMaxCodeLen(Int)`, `reloadDictionary(ByteArray)`, `legalKeys`, `keynamesSerialized`, `dictionaryName`, `tableMaxCodeLen`, `entryCount`, `canExtend`, `wouldExtend(ByteArray)`, `layoutSerialized(ByteArray ctx)`, `layoutFromSourceSerialized(ByteArray source, ByteArray ctx)` — 20 functions (user-engine entry points were removed with user engines). Kotlin externals, delegates and C symbols must stay in sync; mismatches only show up at runtime. `reloadDictionary` calls the Ruby `load_dictionary` on the live engine (no `mrb_close`/`mrb_open`); the Kotlin side falls back to `builtin:mrubyime` if `tableSize()` returns 0.
- `init()` loads all three ireps into the shared `mrb_state` and defines the top-level `keyboard_layout_serialized(ctx)`. `layoutSerialized` calls it with a flat `key=value\n` context (mode/theme/density/editor fields). `layoutFromSourceSerialized` evaluates an imported DSL in a **throwaway `mrb_state`** (`mrb_open` + `mrb_load_irep(keyboard_dsl_irep)` + `mrb_load_string_cxt`), caps the source at **64 KB**, and returns `""` on failure; it never touches the engine state. That evaluation is wrapped in **`mrb_protect_error`** (core; the `mruby-error` gem's `mrb_protect` is not in this build) because an unprotected `mrb_exc_raise` from bad user code aborts the process.
- Host `mruby` 3.3.0 (the `host` build made by `build_mruby.sh`) lacks `MRB_UTF8_STRING` (device build has it), so host-side CJK `length`/`[]` are wrong. For a host build with the **same feature set as the device** (UTF-8 strings, `MRB_ARY_LENGTH_MAX=0`, big GC arena, `mruby-io` + `mruby-time` for profiling) use the committed test config:
  ```bash
  cd mruby && rake MRUBY_CONFIG=host_test_config.rb   # → build/host-test/bin/{mruby,mrbc}
  cat app/src/main/mruby/mrubyime_engine.rb /tmp/prof.rb > /tmp/run.rb && ./mruby/build/host-test/bin/mruby /tmp/run.rb
  ```
  Host timings are ~5× faster than the phone but track it proportionally (full uniliu load: ~1.0 s host, ~2.6 s device with the weighted one-entry-per-line table; the `%phrase` block is most of it — see `mruby-ime/AGENTS.md` for the measured variants).

## Replaceable `.cin` table (`DictionaryRepository` / `CinTable`)

- `DictionaryRepository` resolves `builtin:mrubyime` → `filesDir/dicts/mrubyime.cin` when that copy exists and is sane, else `assets/mrubyime.cin` (uniliu); `builtin:<name>` → `assets/dicts/<name>.cin` (no built-in ships there now; drop a `.cin` in to add one); `user:active` → `filesDir/dicts/active.cin` (+ `getExternalFilesDir(null)/dicts/active.cin` mirror). `dict_id` in `mrubyime_settings` selects it (default `builtin:mrubyime`); a stale `dict_id` that no longer resolves falls back to the default. The Settings label reads `%cname` from the asset.
- **The built-in table ships an editable copy** at `Android/data/<pkg>/files/dicts/mrubyime.cin` (canonical `filesDir/dicts/mrubyime.cin`), exactly like `layouts/keyboard.rb`: `seedBuiltinCopy()` writes it (atomic temp+rename) when missing and **refreshes an untouched seed after an APK update**, while a copy the user edited (`sha256 != recorded`) is never overwritten. An edited copy is what `builtin:mrubyime` loads, so a file manager edit takes effect on the next keyboard show (`signature()` includes the copy's size+mtime, so `onStartInputView` hot-reloads); deleting it brings the shipped table back (「恢復內建碼表」 deletes it too). Seeding runs on the `engine-load` thread; `read()` only uses the copy when `looksLikeCin()` finds `%chardef`/`%cname`/`%ename` in the first 64 KB, and a table that still yields `tableSize()==0` falls back to the shipped asset, so a truncated copy can never brick typing.
- Hot reload: `MrubyimeIME.onStartInputView` compares `dict_id` + `DictionaryRepository.signature()` (id for built-ins, `id:size:mtime` for the user file) and calls `reloadDictionary()` on change — this also picks up an external editor writing the mirror while the IME stays alive.
- Import/export/reset live in the settings 「輸入法碼表（.cin）」 section: import is `ACTION_OPEN_DOCUMENT` (`*/*`, 4 MB cap) and validates with `CinTable.parse` (must contain `%chardef`); `saveUser` writes temp+rename, mirrors to Android/data, and sets `dict_id=user:active`. Export is `ACTION_CREATE_DOCUMENT` (`text/plain`, `<base>.cin`). 「恢復內建碼表」 deletes the user file + mirror and resets the id.
- `%keyname` labels are applied to the keyboard in Chinese mode via `KeyboardView.setDictLabels()`; trivial variants (`a → Ａ`, `, → ，`, `' → ’`, `[ → 〔`) are skipped, so the built-in 形碼 table (which passes an empty map) keeps the classic A-Z look. `a → 日` / `1 → ㄅ` do replace the caps. Long labels use the per-key DSL option **`label_fit: :wrap|:shrink|:none`** (`label_wrap:` = glyphs per line, default 2): `%keyname` labels default to `:wrap`, DSL labels to `:none`. Each key label sits in a cell-sized clipping `FrameLayout`, so anything that still doesn't fit is cut at the cell edge.
- Additional built-ins: drop `<name>.cin` into `assets/dicts/` (see `assets/dicts/README.txt`); no Kotlin change needed. The README file is not `.cin`, so `assets.list()` ignores it.

## Keyboard view invariants (`KeyboardView` / `KeyboardRenderer`)

- `MrubyimeIME.onCreateInputView` loads the layout (`KeyboardLayoutRepository`: runtime engine JSON → `assets/keyboard_layout.json` → small emergency programmatic layout), then builds two **per-page subtrees** (bar + rows) inside `key_bar` (`FrameLayout`) and `key_rows`. Only the active page is visible; duplicate ids across pages are safe because all lookups go through per-page references.
- The built-in Chinese/English layout is one DSL file (`keyboard_layout.rb`); editing it (plus `build_mruby.sh`) changes the keyboard. User-imported layouts use the same DSL in a sandboxed `mrb_state`.
- **User layout**: `layouts/keyboard.rb` (canonical `filesDir/layouts/`, mirrored to `Android/data/…/files/layouts/`) is loaded first when present, validated in the JNI sandbox (64 KB cap), and hot-reloaded by `MrubyimeIME.onStartInputView` via `KeyboardView.setLayout()`. Storage/reconcile logic is in `KeyboardLayoutFiles`. **The settings screen's 「鍵盤佈局（ruby dsl）」 card was deleted on 2026-11-25** — the live keyboard is `keyboard.py`, so there is no UI for importing/exporting a `.rb` any more (the DSL machinery stays as the fallback renderer's source of truth). Historically that card had 匯入／匯出／寫入編輯目錄／恢復內建／用外部編輯器開啟 (`LayoutFileProvider`, the in-app FileProvider replacement); import accepted any file name/MIME (`*/*`) and always stored it as `keyboard.rb`, and export used the MIME `text/x-ruby` (with `text/plain` the Downloads provider appends `.txt`). No storage permission is required. **A failed import explains itself**: the sandbox returns `"\u0001" + message` and `KeyboardLayoutRepository.validateSource()` keeps it, so the settings screen shows `第 N 行（第 M 欄）` plus the offending line for syntax errors and `… (keyboard.rb:N:in …)` for runtime errors (`mrbc_context.capture_errors`).
- **SAF**: `LayoutDocumentsProvider` (authority `${applicationId}.documents`, `MANAGE_DOCUMENTS`, `DOCUMENTS_PROVIDER` filter) exposes **one root that opens straight into `Android/data/<pkg>/files`** (`getExternalFilesDir(null)`, falling back to `filesDir` when external storage is gone) — the same folder a file manager (MT Manager, Material Files) sees on disk — with `layouts/ fonts/ dicts/ sounds/` inside. Document ids are `f:<relative path>`; writes are pulled into the canonical `filesDir/…` copies by the `*.sync()` calls on every keyboard show, and create/delete/rename propagate immediately. Root flags are **`FLAG_LOCAL_ONLY or FLAG_SUPPORTS_CREATE or FLAG_SUPPORTS_IS_CHILD`**, and `COLUMN_MIME_TYPES` must stay unset. `FLAG_SUPPORTS_IS_CHILD` is **required for the folder picker** (`ACTION_OPEN_DOCUMENT_TREE`): DocumentsUI's `ProvidersAccess` filters with `state.action == ACTION_OPEN_TREE && !root.supportsChildren()`, so without it the root appears in file pickers but a file manager cannot pick the folder to get a persistent grant. `COLUMN_MIME_TYPES` set ⇒ the root is dropped from `*/*` pickers.
- IR: `GridSpec` (12 columns in the built-in layout, `gapH`/`gapV`/`outer` — built-in is `0/0/0`), `HeightSpec` (bar 48 / body 240), `PaddingSpec`, `ThemeSpec` (`dark`/`light` token maps + states), `PageSpec`, `BarSpec` (buffer/candidates/group slots + keys + optional inset `border: { width:, color:, style:, side: }`), `RowSpec`/`KeySpec` (span, weight, align, action, gestures, repeat, long-press, font, style), `ChipSpec` (`style.border:` = every unselected chip, `style.selected.border` = the selected one; `BorderSpec.style` is `solid`/`dashed`/`dotted` and `side` narrows it to one edge). Dashes need `BorderedPlateDrawable` (a hand-rolled `Drawable`) because `GradientDrawable.setStroke()` only draws solid lines.
- Geometry is handled by `KeyRowLayout`: `span` = fixed share of the `columns` grid (12 in the built-in layout), `weight` = flex share, `align` = start/center/end/space_between; gaps come from the DSL in **dp** (`grid gap_h`/`gap_v`/`outer`, `bar gap:`, group/status `gap:`) and are **all 0 in the built-in layout** (flushest keys, `outer: 0` so the keyboard sits flush against the window edges — a positive `outer` would show a `#1C1C1E` band down the sides in Dark Mode; parser defaults when omitted are 1/1/0.5). **Edges are computed from the grid** (`round(outer + cumulativeSpan·unit)`), so rows with different key counts align on the same vertical seams; a row's spans should sum to `columns`. Bar row weights: buffer **2** + candidates **9** + hide **1** = 12 (the 編碼區寬度 slider defaults to 「跟隨版面」; once moved it replaces the buffer weight and candidates absorb the difference).
- Candidate chips are **pooled, never rebuilt**: `updateCandidates()` keeps one `TextView` per candidate, adds/removes only the delta, swaps `text` only when changed, and repaints the plate only when selection/theme changed (`styledSelection`/`styledTheme`). Chips are **24sp bold `n字`**, identical `minimumWidth` (width of `0微` + PadH 3 dp); the border is DSL-driven (`candidates border:` = every chip, `border_selected:` = the active one → `paintChip()` → `chipBorderDrawable()` → `BorderedPlateDrawable`). The built-in Chinese page sets `border: { width: 1, color: :seam, style: :dotted }` (subtle dotted frame, invisible in Light since `seam` is white) and `border_selected: { width: 2, color: :ink, style: :solid, side: :bottom }` (the 2 dp selection rule); a layout without them falls back to `chip_hash`'s legacy 3 dp bottom rule. Empty state shows one **placeholder chip** (same `border_selected` in Chinese, plain in English).
- Buffer: **24sp bold**, uppercase, **no frame**, box width **2 units** in the built-in layout (the 編碼區寬度 setting defaults to 跟隨版面; moving it overrides the buffer weight and the candidate row absorbs the difference), shows the **last 6** codes when long (`ellipsize=start`); tapping commits the raw code, swiping **up** commits the inline-composing text (`inline_composing_mode`). Buffer and chip text share one baseline (`includeFontPadding=false`, chips also `setFallbackLineSpacing(false)`).
- The bar is one row: buffer → `StepScrollView` candidate chips → hide `▼` (Chinese), or a 12-key action bar (`TAB`, blank, `^A ^C ^V`, arrows, `DT`, `W`) → hide (English). No pagination/arrows/page number. `StepScrollView` tracks the finger on drag, snaps to full-page boundaries, and **loops**; hardware D-pad up/down calls `stepPage()`.
- Gestures/actions come from the IR through one dispatcher (`KeyboardView.dispatchAction`, used by tap + `long_press` + `gestures:`): `code`, `space`, `backspace` (400 ms / 80 ms repeat), `enter`, `ime_hide`, `toggle_mode`, `combo` (`value: "ctrl+shift+1"` → `MrubyimeIME.sendKeyCombo`, sends DOWN/UP with meta), `key_event` (`ins/del/home/end/pgup/pgdn/tab/capslock/menu/f1-f12/…`), `modifier` (sticky one-shot ctrl/shift/alt/meta latch, underlined label, applied to the next key), `date`/`time`/`weekday`/`datetime` (`value:` = SimpleDateFormat pattern, evaluated at tap time), `dpad`, `clipboard`, `noop`; space also handles `toggle_mode`/`cursor_left`/`cursor_right` swipes, and English letter keys emit the uppercase letter on swipe-up (>16 dp) unless the key declares its own `gestures:` (a gesture hash accepts `{ action:, value: }` as well as the short `{ a:, v: }` form). `sub_label:` renders a small label at the key's top-right.
- Key seams: `keyBorder` is painted **per side** (right+bottom always, left on the first column, top on the first row) by `KeyboardView.gridKeyDrawable`, so flush neighbours share one 1 dp line; a full `setStroke()` per key doubles every internal line. Both themes set it (Light black `#000000`, Dark `#1C1C1E` — the same deep tone as `seam`, so the dark grid is visible against the `#3A3A3C` keys). Per-key text alignment is `align: :left/:center/:right` (label gravity), row-level is `row align:` (only visible when the row's spans sum to less than `columns`).
- Mode labels and sound are DSL-driven too: `label_zh`/`label_en` (+ `sub_label_*`) swap key text on mode change via `KeyboardView.applyModeLabels()` (actions are **not** swapped); `sound :click, volume: 0.6` (layout) plus `sound:`/`sound_volume:` (per key) play an `AudioManager` system click (`android.view.SoundEffectConstants` — `AudioManager.SoundEffectConstants` is `@hide` and does not resolve) or a `SoundPool` file from `assets/sounds/`, an absolute path or `filesDir/sounds/`; `haptic:` is wired to `performHapticFeedback`. Default is silent.
- Only the **first page** (`defaultPage`) and a page named `english`/`en` are shown; `page when:` conditions only decide whether a page is built. Some DSL options are parsed but not rendered yet: `icon:`, `min_touch`, `theme … state`, `candidates autoscroll:`, and `long_press` other than `toggle_hide_rows`. `font:` **is** rendered now (`buffer`/`candidates`/per-key `size:` and `weight:`), because it replaced the removed settings sliders.
- Status lamps are a bar slot: `status span: …, gap: … do lamp :caps/:shift/:ctrl/:alt/:meta/:english/:latch/:buffer/:candidates, label: "A", span: 1 end` (`indicator` is an alias). They become `StatusSlot`/`LampSpec` in the IR, are built by `KeyboardRenderer.createLampView()` into a nested `KeyRowLayout`, and are exposed as `PageViews.lamps` / `KeyboardView.updateStatusLamps()` — not as `KeyView`s, so they never dispatch actions. Lit state = physical modifiers (`KeyEvent.metaState` from `onKeyDown`/`onKeyUp`) **or** the sticky `modifierLatch`. `lampOn`/`lampOff` tokens are **ink** colours (lit = `lampOn` -> `ink`; dim = `lampOff` -> `keyBorder` -> `ink`, blended 35 % toward the bar plate), so one token per theme is enough — never make them background colours.
- Theme: both `MrubyimeIME` and `MrubyimeSettingsActivity` listen to `light_theme`; `KeyboardView.lightTheme` re-renders from the IR theme (`ThemeResolver`). Dark: bar/keys `#3A3A3C`, seams/`keyBorder` `#1C1C1E` (a 1 dp per-side grid now drawn in Dark Mode too), white ink. Light (e-ink, default): bar white `#FFFFFF`, keys white with a 1 dp black **per-side seam** (no press state, so shared edges stay 1 dp), seams white, black ink; the selected chip / Chinese placeholder has a 2 dp black bottom rule and **both** bars (Chinese and English) a 1 dp black top rule (the dotted `seam` chip frame is white-on-white there). Because `keyBorder` is set in both themes, the built-in keys are always plain plates (no press selector); `keyPressed` survives only for the `flat` punctuation/hide keys on the candidate bar. Optional colour tokens resolved by `KeyboardView.themed()` (`bar`/`barInk`, `buffer`/`bufferInk`, `chip`/`chipInk`, `chipSelected`/`chipSelectedInk`/`chipMark`, `key`/`keyInk`/`keyPressed`/`keyBorder`, `seam`, `muted`, `lampOn`/`lampOff`); per-key `ink:`/`bg:`/`style: { border:, radius: }` override them.
- **Bar / chip borders come from the DSL too**: `bar … border: { width:, color:, style:, side: }` frames the whole candidate bar **inset** (the bar container is padded by the width, so content and the 12-column grid shift inwards and the frame is never clipped by the IME window); `candidates … border:` frames every unselected chip and `border_selected:` the active one. `style:` is `:solid`/`:dashed`/`:dotted`, `side:` defaults to `:all` (`:bottom` reproduces the classic bottom underline). Default width `0` = no frame; the built-in uses a 1 dp `:top` rule on **both** bars (Chinese and English), plus a dotted `:seam` chip frame and a 2 dp `:bottom` selection rule on the Chinese candidate row. Each page is inset by **its own** border width, so a page without `border:` keeps full width. Dash/dot strokes are painted by `BorderedPlateDrawable` (`KeyboardView.borderedPlate()` / `borderEffect()`) — `GradientDrawable` can only do solid strokes.
- **Size and type come from the DSL only**: `height bar:` / `height body:` / `padding left:/right:/bottom:` decide the keyboard height (`bar + body + bottom`, or `bar + bottom` when key rows are hidden), `buffer weight:` / `candidates weight:` the bar split, and `buffer font:` / `candidates font:` / per-key `font:` the text sizes. The settings page no longer has sliders for bar height, body height, paddings, buffer width or fonts, and the old prefs (`candidate_bar_height`, `keyboard_body_height`, `keyboard_*_padding`, `candidate_font_size`, `key_font_size`, `buffer_width_weight`) are ignored — 「恢復內建佈局」 is how you go back to defaults.
- Keyboard height: clamped to screen height and enforced with `EXACTLY` in `KeyboardView.onMeasure`; left/right/bottom padding via `setPadding`. Never assign a plain `ViewGroup.LayoutParams` to the attached `keyboardView` — mutate the existing `layoutParams`.
- Lifecycle/UX details (settings sections, navigation bar, hide button, hardware key map, inline composing, dead-code gates) are documented in `mruby-ime/AGENTS.md`; keep both files in sync when behavior changes. Hiding the keyboard **drops the composition** (`clearCompositionBeforeHide()` on the ▼ tap, `onWindowHidden` and `onFinishInputView` — nothing is committed), so a half-typed code never stays behind in the field as inline composing text.
